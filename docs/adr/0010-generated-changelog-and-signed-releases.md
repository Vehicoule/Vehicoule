# 0010. Generate the changelog from commits and sign every release

- Status: Proposed
- Date: 2026-11-06
- Deciders: the user

## Context

Nothing is released yet. The user agreed on 2026-11-06 to a changelog generated from the commits and to signed
releases; this ADR fixes how, so that the first release does not invent it.

- Commit subjects already follow `<area>: <What the change does>` (AGENTS.md, Conventions), regular enough to group by
  area.
- `git-cliff` 2.14.2 (crates.io, released 2026-09-18, `MIT OR Apache-2.0`) writes a changelog from Git history with
  configurable grouping. `release-plz` 0.4.3 (crates.io, released 2026-11-02, `MIT OR Apache-2.0`) also bumps versions
  and opens a release pull request; it is built for crates published to crates.io, which the app's crates are not
  (`publish = false` in the root `Cargo.toml`).
- GitHub's `actions/attest-build-provenance` (latest tag `v4.2.2`) signs a provenance statement for each built file
  with Sigstore, tied to the workflow and commit that built it, with no key to keep; `gh attestation verify` checks it.
- An Android app is signed with a key of its own; losing that key means users cannot update to a new version signed
  with another key.
- F-Droid can verify that its build of an app matches the developer's (reproducible builds).

## Options

1. **`git-cliff` for the changelog, tags signed by the user, provenance attested in the release workflow, the Android
   key kept offline with a backup.** Each piece small; the release workflow is written with the first release.
2. **`release-plz`.** Versions and changelog in one tool; designed around crates.io publishing, which this repository
   does not do.
3. **A changelog written by hand.** No tool; drifts from what was merged.

## Decision

Recommended: option 1.

- `CHANGELOG.md` is generated by `git-cliff` at each release, grouped by area, and committed in the release pull
  request.
- Release tags are signed (`git tag -s`) by the user.
- Each released file gets a provenance attestation from the release workflow.
- The Android signing key is created offline, backed up in two places the user chooses, and never stored in CI as a
  plain file.
- Reproducible builds are a goal, measured when the first Android build exists.

## Consequences

- The first release pull request adds `cliff.toml`, the release workflow and the attestation step; each is pinned like
  the rest of CI.
- A commit subject that breaks the convention shows in the changelog, which makes the convention matter more.
- Losing the Android key remains the one unrecoverable mistake; its backup is the user's to keep.
